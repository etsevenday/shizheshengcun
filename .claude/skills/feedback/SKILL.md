# 留言板处理流程

每条留言走完下面 7 步才算处理完。多条留言时逐条走，不要把几条合在一次提交里，除非它们改的是同一处。

## 0 约定（整个流程都要遵守）

- 规则与数值的唯一来源是 `doc/策划案/` 下的策划案；`data/config.v0.4.json` 里的数值不能自己改，策划案没写的规则不能自己补（见 `doc/实施方案 v0.1.md` 第 9 节、`doc/开发计划 v0.2 交互与地图扩展.md` 第 8 节）。
- 这个工作区常有别的会话同时在改文件：提交前先 `git status`，只 `git add` 自己改的具体路径，禁止 `git add -A` / `git add .`。
- `feedback-inbox/`、`.feedback.local.json` 在 .gitignore 里，玩家截图、存档、密钥都不入库，也不要贴进对话或提交说明。
- 全程用中文和用户沟通，用户熟 Unity/C#、不熟网页，解释网页问题时多用 Unity 类比。

## 1 拉取

```bash
python tools/feedback.py list
```

```bash
python tools/feedback.py pull
```

输出“没有留言。”就直接告诉用户没有新留言，结束。否则每条留言在 `feedback-inbox/<时间>-<编号>/` 下，读 `feedback.md`（正文、环境、游戏状态、最近日志），看截图 `*.webp`，`save.json` 是玩家当时的存档。只处理 `list` 里状态为 new 的；inbox 里更早的目录是已处理过的，不要重做。

## 2 分类，决定“改”还是“问”

逐条给出判断并先写进对用户的汇报里，再动手：

| 情况 | 处理 |
| --- | --- |
| 报错、卡死、显示错位、按钮无效、与策划案写明的行为不一致 | **bug，直接改**。先 `mark <编号> doing`。 |
| 描述看不懂、截图与文字对不上、复现不出来 | **问用户**。写清你试了什么、看到了什么，给出你猜的两三种可能，让用户选。 |
| 需要新数值、新规则、改平衡（分类“数值/难度”“建议”，或 bug 的修法有多种且策划案没规定） | **问用户**，不要自己定。`mark <编号> doing --note "等策划确认：……"`，让留言的人在留言墙上看到在等什么。 |
| 策划案已明确不做的（例如按住连续转移） | 先告诉用户，等用户说 wontfix 再标。 |

问用户时用 AskUserQuestion，一条留言一个问题，选项写成具体的改法而不是“是/否”。用户回答后按答复进入第 3 步。能先做的（不依赖答复的部分）先做。

## 3 修复

1. **复现**：按 `feedback.md` 的游戏状态与最近日志在脑中或内核测试里重走一遍；界面问题用内置浏览器起本地开发版（`preview_start {name: "web"}`，5177 被占时用 `web-alt` 5180），用 `javascript_tool` 把 `save.json` 的内容写进 `localStorage` 的 `survival.save.v1` 后刷新、点“继续”，就能回到玩家出问题的那一刻。
2. **改代码**：内核规则在 `src/Core/`，界面在 `web/Survival.Web/Components/`、`Services/GameSession.cs`、`wwwroot/css/app.css`。内核改动要补或改 `web/Survival.Core.Tests/` 里的用例。
3. **跑测试**：

```bash
dotnet test web/Survival.sln
```

全绿才进入第 4 步。测试失败就修到绿，修不了回第 2 步问用户。

## 4 另起 Fable 5.1 会话试玩验证

自己改的东西不能只靠自己点两下。用 `mcp__ccd_session__start_session` 起一个**独立会话**专门玩，参数：

- `initiation: "user_asked"`（用户在流程里要求的），`context: "fresh"`，`use_worktree: false`（它只读不改，共用这份工作区），`wake_when_done: true`。
- `model` 留空即继承本会话；本会话不是 Fable 5.1 时显式传 `claude-fable-5-1`。
- `title`：`试玩验证 留言 <编号>`。
- `background`：项目一句话介绍、试玩地址只用本地开发版、规则来源是策划案、它的任务只是玩和报告。
- `prompt` 必须包含：
  1. 留言原文（去掉称呼等个人信息）和你改了什么、改在哪几个文件。
  2. 怎么起服务器：`preview_start {name: "web-fb"}`（5190 端口，专给试玩会话用，避免和主会话抢端口）。
  3. 怎么回到出问题的那一刻：`feedback-inbox/<目录>/save.json` 写入 `localStorage.survival.save.v1` 后刷新、点“继续”；也要从新开局再走一遍相关操作。
  4. 要检查什么：留言里的问题是否消失；相关的其他路径是否还正常（例如改了拾取就同时试拖拽、箭头、数量框）；控制台（`read_console_messages`）有无报错；1280×720 下有无裁切。
  5. 禁止事项：不改任何文件、不提交、不 mark 留言、不去线上地址玩。
  6. 报告格式：每项“通过／未通过”，未通过的写复现步骤、看到的现象、截图。

等它结束（应用会在它结束时唤醒本会话），读它的报告，**自己核对一遍**再下结论：未通过的回第 3 步改，改完再起一轮试玩；两轮仍不过就把现象整理好问用户。

## 5 更新上线

1. `git status` 核对改动文件，`git add <具体路径>`。
2. 提交说明第一行：`留言 <8位编号>：<玩家能感知的改动一句话>`；正文写改法要点；结尾加 `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`。
3. `git push origin main`，然后等待发布：

```bash
gh run watch --exit-status
```

发布流程会先跑一遍内核测试再部署到 https://etsevenday.github.io/shizheshengcun/ ，大约 1～2 分钟。失败就读日志修掉，不要跳过。

## 6 公开回复并标记

```bash
python tools/feedback.py mark <编号> done --note "已处理（提交 <短号>，推送后几分钟内上线，刷新页面即可）。

改动：
1. ……玩家能感知的新行为是什么、怎么操作。
2. ……

未改：……这次没做的部分及原因（没有就删掉这段）。"
```

备注会作为“作者回复”公开显示在留言墙上，留言的人看不到代码，所以不能只写“已修复”和提交号。不处理的用 `wontfix`，备注写明原因（引用策划案哪一条）。

## 7 必要时同步策划案

改动如果**改变了策划案里写明的行为、补了策划案没写的规则**，或**用户在第 2 步拍板了新做法**，要同步文档，和代码同一次提交或紧接着一次提交：

| 改了什么 | 写到哪 |
| --- | --- |
| 界面交互与策划案描述不同了 | 对应策划案条目原地改写，开头加【实现同步】并注明“（留言 <编号>）”，参照 `doc/策划案/UI策划 v0.1/适者生存基础系统UI策划案 v0.1.md` 里已有的写法 |
| 规则或数值由用户新拍板 | `doc/开发计划 v0.2 交互与地图扩展.md` 第 8 节“B 表策划答复”加一条，注明日期 |
| 任何已处理留言 | `doc/开发计划 v0.2 交互与地图扩展.md` 第 1 节“留言墙对照”表加一行：编号、留言要点、处理结果（提交号）、涉及哪份策划案 |
| 第 4 步的试玩验证 | `doc/试玩记录 v0.1.md` 第 4.1 节表格加一行：项目、结果、实测现象 |

纯 bug（实现本来就偏离了策划案，改回去）不改策划案，只补留言墙对照与试玩记录。

## 8 收尾汇报

给用户的汇报按留言分条：编号、分类判断、改了什么（文件）、试玩结论、提交号、留言墙回复摘要、策划案改了哪里；等用户拍板的单独列出并把问题再问一次。
