# 新策划案接入流程

一份新策划包从"目录里出现"到"线上可玩"走完下面 8 步。整个流程本会话只做协调与核对，代码由开发代理写，试玩由试玩代理做。**全程用当前会话的默认模型**：起代理时不传 `model`（让它继承本会话），不要指定 `fable`（太贵，用户 2026-10-26 明确要求不用）或别的型号；上一次的实例是 v0.4（提交 8b4d7db…831b2af，计划文档 `doc/开发计划 v0.3 卡片统一与设施烹饪.md`），照它的样子做。

## 0 约定（全程遵守）

- 规则与数值的唯一来源是飞书知识库里的策划案（第 1 步抓成本地快照后再读）；`data/config.v0.4.json` 里的数值不能自己改，策划案没写的数值绝不自补。策划案没写的**规则**可以由开发解释，但必须写成"开发假设"表（见第 2 步），不含数值。
- 工作区常有别的会话同时改文件：提交前 `git status`，只 `git add` 自己改的具体路径，禁止 `git add -A`/`git add .`；不碰 `web/Survival.Web/wwwroot/js/feedback-widget.js`、`supabase/`、`tools/supabase-feedback.sql`、`doc/留言板接入说明.md`；别的会话放进来的未入库文件不动、不提交。`doc/策划案.7z` 之类压缩包不入库。
- 开发阶段**不推送**，推送 = 发布到 https://etsevenday.github.io/shizheshengcun/ ，只在用户明确说"推送/上线"后做。
- 全程中文；用户熟 Unity/C#、不熟网页，解释网页问题多用 Unity 类比。

## 1 从飞书取策划包并落成本地快照

策划案的唯一来源是飞书知识库「生存日志 › 策划案」（根页 https://zcngxk349rhs.feishu.cn/wiki/TiTAwsHh8iBhwYkPNOCcK7tPnhd ，结构见记忆 `feishu-wiki-docs`）。仓库里 `doc/策划案/` 只是开发用的**快照**，每次接入前必须重新抓，不能拿旧快照当依据；策划在飞书上追加的【实现同步】和跨版本提示（例如 v0.4 的 00 案开头插的 v0.7 说明）也只有飞书上有。

没有飞书连接器，用内置浏览器（已登录，登录态会保留；遇到登录页就请用户在浏览器面板里登录，不要自己输密码）：

1. `preview_start {url: 根页}`，`resize_window {width:1400,height:900}`；知识库树在左栏，`find "策划案"` 后点节点左侧三角展开，找到新版本节点（如「卡片统一与设施烹饪 v0.4」）。点树里的**文字**打开页面（点到了只会出 tooltip，要确认 URL 变成新的 `/wiki/<token>`）；版本页本身也可能有正文和附件（如「策划增量配置 vX.json」），子页面逐个打开。
2. 每篇正文按下面三段式抓成 Markdown（飞书按可见区域懒渲染，且**只认真实滚轮**，程序改 scrollTop 不会触发渲染）：
   - `Read` 读 `.claude/skills/design-dev/scripts/feishu-dump.js`，把全文原样贴进 `javascript_tool` 执行一次（返回 "ready"，并把页面滚到顶）。
   - 用 `browser_batch` 循环：`computer scroll`（坐标取正文中央，down，amount 8；注意 `resize_window` 后 `computer` 的坐标系仍是截图报告的 800×600，按它给坐标）→ `wait 1` → `javascript_tool "window.__fs.collect()"`，直到 collect 返回 `bottom:true` 且 `total` 不再增长（一次批处理最多 25 个动作，长文分几批）。
   - `javascript_tool "window.__fs.final()"` 取 `{title, markdown, images, files}`；用 `Write` 写到 `doc/策划案/<版本名>/<页名>.md`（页名用飞书标题，去掉 " - 飞书云文档"）。表格已转成 Markdown 表，图片是 `![图片n](assets/图n.jpg)` 占位。
3. 附件（JSON 等）：在含附件的页面执行 `scripts/feishu-attachment.js`，它从文件块的封面地址取 token、走同源地址读文本，不触发浏览器下载；把 `text` 写成 `doc/策划案/<版本名>/<附件名>`。**不要点飞书的"下载"按钮**（会往浏览器下载目录落文件）。
4. 图片（策划截图、红框图）：`javascript_tool "window.__fs.image(n)"` 把第 n 张图滚进视口并返回 CSS 坐标；先 `resize_window {preset:"desktop"}` 让坐标系一致，再 `computer zoom` 该区域、`scale 1`，结果里给出的 png 路径复制到 `doc/策划案/<版本名>/assets/图n.jpg`。截图分辨率受面板尺寸限制，细节看不清时让开发代理直接在浏览器里看原页；需要原图时可用 `fetch(img.src)` 转 base64 分段（每段 ≤10 万字符）回传后 `base64 -d` 落盘，这一步交给便宜的子代理做，别让主会话吞 50 万字符。
5. 抓完对照飞书页核对：标题数、表格行数、章节顺序（脚本按文档纵坐标排序，但渲染不完整时会缺段，缺了就再滚一遍补 collect）。**表格的行也懒渲染**：长表格滚出视口时末尾几行只剩空单元格，要把表格 `scrollIntoView` 后直接 `querySelectorAll('tr')` 读末尾几行核对，缺行再补。快照目录随第一个里程碑一起入库。

整页读法太慢时（只想先看一眼），`get_page_text` 只能拿到当前渲染出来的那一屏，不要拿它当全文。

## 2 plan mode 分析

用 `EnterPlanMode`，然后：

1. **并行起两个 Explore 代理**（一个内核 `src/Core`，一个网页壳 `web/Survival.Web`），brief 里把新策划案的核心变化讲清楚，要求对方回答"现在怎么实现、改哪些文件、哪些函数可复用"，带路径与行号。要搜索广度 very thorough。
2. 自己读：`doc/开发计划 v*.md` 最新一份（第 8 节假设表的写法与"本包不做"）、上一轮的"实现同步"记录、`GameState.cs`、`.claude/launch.json`（端口）。
3. 写计划文件（plan 模式给的路径），结构固定：
   - **背景与结论**：三块变化（界面 / 内核 / 存档），以及"需不需要用户补信息"的明确结论。策划案把数值、进程参数、迁移规则、验收用例都给齐时，结论就是不需要。
   - **执行方式**：开发代理 + 试玩代理 + 本会话核对；提交约定。
   - **开发假设**：编号列表，只写"规则解释"（ID 写法、状态落在哪个类、Esc 顺序、迁移冲突时玩家看到什么、图片用占位等），不含任何数值。
   - **工程映射与里程碑**：编号接着上一轮（v0.4 用到 M25，下一轮从 M26 起），每个里程碑列文件、改法、测试；通常顺序是 配置与物品 → 模型 → 规则/tick → 拖拽与预览 → 存档迁移 → 界面 → 次级菜单 → 收尾（文档、README、SurvivalBot）。
   - **可直接复用**：函数与组件清单，让开发方别重写。
   - **验证**：`dotnet build web/Survival.sln`（`dotnet test` 只编译测试工程，网页壳的编译错误要靠它暴露）与 `dotnet test web/Survival.sln`、策划案里的验收编号（U/P 系列）、两档分辨率截图、旧档写入 `localStorage.survival.save.v1` 后点"继续"。
   - **试玩检查清单**：必走路线 + 报告格式。
4. 真正阻塞的空白（不问就只能补数值）用 `AskUserQuestion` 问；能用假设绕过的不问。然后 `ExitPlanMode`。

## 3 开发（开发代理）

用户批准计划后立刻开发。**注意**：批准计划之后的回合会被应用当作自动事件，`start_session` 会报"Start sessions only on the user's own words"，不要反复试；直接用 `Agent`：

- `subagent_type: "general-purpose"`，**不传 `model`**（继承本会话默认模型），在本工作区工作（不开 worktree）。
- prompt 必须自包含（代理看不到本会话）：项目背景与约定（第 0 节）、任务与提交规则（每里程碑一提交、不推送、Co-Authored-By 写代理自己实际的模型名）、先读哪些文件、**现有工程关键事实**（探索代理查到的路径与行号，直接贴）、**开发假设**全文、里程碑映射全文、可复用清单、完成标准（测试全绿、浏览器逐条走验收编号、两档分辨率截图、旧档验证、`preview_stop`）、最终汇报格式（提交号、测试数、手测逐条、偏差、待确认、资源缺失清单）。
- 告诉它遇到假设没覆盖的规则空白：选最保守做法继续并在汇报里列"待确认"，不要停下来等人。
- 手测用 `preview_start {name:"web"}`（5177，被占用 `web-alt` 5180），不要用 Bash 起服务器。
- 要求它写 `doc/开发计划 v<下一号> <策划包名>.md`（格式照 v0.3：映射、假设、实施记录与偏差、待确认、资源缺失）并更新 README 文档表。

代理结束后自己核对：`git log --oneline`、`git status`（应只剩别人的未入库文件）、`dotnet build web/Survival.sln` 0 错误与 `dotnet test web/Survival.sln` 全绿、看它的截图。

## 4 试玩（试玩代理）

`Agent`，`subagent_type: "general-purpose"`，**不传 `model`**（继承本会话默认模型）。prompt 要点：

- 身份：真人玩家视角，**只玩和报告**，不改文件、不提交、不推送、不去线上地址。
- 背景：这次改了什么（按策划案要点写，让它知道预期），规则以哪份策划案为准，开发方解释在哪份开发计划；报告里要区分"与策划案不符"和"策划案如此但体验不好"。
- 怎么玩：`preview_start {name:"web-fb"}`（5190，专给试玩用），首次加载约 10MB 耐心等；`read_page`/`get_page_text`/`find` 读界面，`computer` 点击与 `left_click_drag` 拖拽，关键画面截图；视口 1280×720 为主、1600×900 复查；快捷键 M/C/R/L/Esc。
- 必走路线：从新游戏至少玩到本次改动涉及的目标完成（v0.4 是第 3 日目标），逐项列出要触发的交互（本次新增的每条路径、熄火复燃、超重拒绝、刷新读档、旧档迁移、Esc 逐级、拖拽中 Esc）。
- 全程留意：控制台报错、裁切重叠、热区过小、文案错误、图标缺失、数据不一致。
- 报告格式：试玩过程表（时刻、行动、六项状态，样式照 `doc/试玩评价与改进建议 v0.1.md`）、Bug 清单按严重度（复现、预期引用策划案条目、实际、截图文件名、报错原文）、验收对照（每条通过/未通过/未覆盖）、可以改进的地方、总体评价。结束 `preview_stop` 并 `resize_window {preset:"desktop"}`。

## 5 分类试玩结果

| 情况 | 处理 |
| --- | --- |
| 违反策划案条目、同一功能两条路径信息不一致、1280×720 裁切/热区 <40px、控制台报错、残留选中态 | **bug，交回开发代理修**：`SendMessage` 给同一个开发代理（它保留上下文），逐条写编号、复现、要求、截图文件名；要求一次提交（M 下一号，"试玩修复：…"）、测试全绿、两档分辨率亲自复验、在开发计划里加"试玩修复"一节 |
| 策划案没写但明显更好的小改（如可见的禁用原因、与另一路径对齐的文案） | 一并交给开发代理 |
| 体验改进（提示时机、动画时长、数值手感）、策划案空白需要新规则 | **不做，列给用户拍板** |
| 开发代理汇报里的"待确认" | 原样转给用户 |

修完后 `SendMessage` 给同一个试玩代理做**复验**：逐条核对修复项 + 一轮快速回归（营地主流程、读档、Esc、控制台）。复验仍不过就再来一轮；两轮不过整理现象问用户。一两行能修的（比如一个 CSS 值）自己直接改并提交，不必再绕代理。

## 6 汇报与上线

汇报分四段：做了什么（里程碑与提交号、测试数、试玩结论一句话）、待用户确认的规则、待拍板的体验改进、需要知道的事（例如代理误清了哪个端口的本地存档）。用 `wrap_up` 问"现在推送 main 上线吗"。

用户说推送后：

```bash
git push origin main
```

```bash
gh run list --limit 1 --json databaseId,status,conclusion
```

拿到 run id 后 `gh run watch <id> --exit-status --compact`，失败读日志修掉；成功后 `curl` 线上地址确认 200，再汇报。

## 7 记忆与后续

- 流程本身有新经验（新的坑、新的端口、新的代理限制）写进记忆 `opus-dev-fable-playtest-pattern.md`，不要重复写仓库里已有的内容。
- 用户拍板了待确认项后，按 `/feedback` 第 7 步的方式同步策划案与开发计划 B 表，再走一次小的"修改 → 测试 → 复验 → 推送"。策划案正文在飞书，本地快照不是源：【实现同步】段落写进开发计划文档，并在汇报里给出可直接粘贴到飞书对应位置的段落；用户明确要求时才用内置浏览器在飞书页里打字插入（点到目标段落末尾，`type` 文本，插入后 `get_page_text` 核对），不要自行改动策划原文。
