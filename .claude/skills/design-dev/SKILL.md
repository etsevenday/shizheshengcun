# 新策划案接入流程

一份新策划包从"策划推到 git"到"线上可玩、仓库里的策划案与实现一致"走完下面各步。整个流程本会话只做协调与核对，代码由开发代理写，试玩由试玩代理做。**全程用当前会话的默认模型**：起代理时不传 `model`（让它继承本会话），不要指定 `fable`（太贵，用户 2026-10-26 明确要求不用）或别的型号；上一次的实例是 v0.4（提交 8b4d7db…831b2af，计划文档 `doc/开发计划 v0.3 卡片统一与设施烹饪.md`），照它的样子做。

## 0 约定（全程遵守）

- 规则与数值的唯一来源是仓库 `doc/策划案/`（策划用 Codex 提交推送，第 1 步拉取后再读）；`data/config.v0.6.json` 里的数值不能自己改，策划案没写的数值绝不自补。策划案没写的**规则**可以由开发解释，但必须写成"开发假设"表（见第 2 步），不含数值。
- 工作区常有别的会话同时改文件：提交前 `git status`，只 `git add` 自己改的具体路径，禁止 `git add -A`/`git add .`；不碰 `web/Survival.Web/wwwroot/js/feedback-widget.js`、`supabase/`、`tools/supabase-feedback.sql`、`doc/留言板接入说明.md`；别的会话放进来的未入库文件不动、不提交。`doc/策划案.7z` 之类压缩包不入库。
- 开发阶段**不推送**，推送 = 发布到 https://etsevenday.github.io/shizheshengcun/ ，只在用户明确说"推送/上线"后做。
- main 现在有两个人推：策划（经 Codex）推 `doc/策划案/`，本方推代码与文档。每次推送前先 `git pull --rebase --autostash origin main`，不强推（`--force` 禁用）。
- 全程中文；用户熟 Unity/C#、不熟网页，解释网页问题多用 Unity 类比。
- 由本机定时任务 `/git-watch` 无人值守触发时，凡本技能里"问用户 / 等用户点头 / 用户拍板"的步骤按 `git-watch` 技能第 4 节改：写进待确认问题文档、跑完就推、开 issue 提醒策划。

## 1 从 git 拉取策划包

2026-10-27 起和策划的合作改走 git：策划不熟 git，由 Codex 帮他把新策划案（或对旧策划案的修订）提交并推送到 `main` 的 `doc/策划案/` 下，给 Codex 的约定写在仓库根目录 `AGENTS.md`（开发方这边不自动加载它，要核对策划的放置、答复、自查约定时用 Read 读）。飞书知识库「生存日志 › 策划案」已停更，只当历史参考，不再从那里抓。

1. 先看远端带来了什么，再合入：

   ```bash
   git fetch origin
   ```

   ```bash
   git log --oneline --stat HEAD..origin/main
   ```

   `git diff --stat HEAD...origin/main -- doc/策划案`（三个点：只看远端这边的改动）列出这次策划改了哪些文件。远端没有新提交 → 问用户策划案在哪（可能还没推，或推到了别的分支）。远端提交碰了 `doc/策划案/` 以外的文件（代码、`data/`、`web/`、`.github/`）→ 先列给用户确认再合入。
2. `git pull --rebase --autostash origin main`。冲突多半出在本方加过【实现同步】或「修改记录」的策划案文件：策划改的原文以策划为准，本方的【实现同步】句子和修改记录条目保留；两边改了同一句、拿不准怎么合就停下问用户，不要替策划定。
3. 确认这次要接入的内容：
   - 新版本目录（如 `doc/策划案/<名称> v0.8/`）就是这次的策划包；对旧版本文件的修订也算本次要求，用 `git show <策划的提交号> -- doc/策划案` 逐个看 diff。
   - 文件不是 Markdown（docx/xlsx/pdf）：在 scratchpad 里转成文本读（docx 是 zip，读 `word/document.xml`；xlsx 用 python 读表；本机没有 pandoc），转出的文件不入库；要把它整理成 md 入库先问用户。
   - 文件放乱了（丢在 `doc/策划案/` 根下、没带版本号、改了旧文件名）不要自己挪，告诉用户让策划下次按 `AGENTS.md` 放；本次照现状读。
4. 全文通读新策划包，留意文首的跨版本说明，以及旧版本文件里本方之前写的【实现同步】（那是现行实现；新策划案推翻它时按新的来，计划里写明）。

## 2 plan mode 分析

用 `EnterPlanMode`，然后：

1. **并行起两个 Explore 代理**（一个内核 `src/Core`，一个网页壳 `web/Survival.Web`），brief 里把新策划案的核心变化讲清楚，要求对方回答"现在怎么实现、改哪些文件、哪些函数可复用"，带路径与行号。要搜索广度 very thorough。
2. 自己读：`doc/开发记录/` 里最近的一两份（假设表的写法与"本包不做"；2026-11-11 起每个批次一份，之前的在 `doc/开发计划 v*.md`，那几份很大，用 Grep 按批次号找，不要整份读）、上一轮的"实现同步"记录、`GameState.cs`、`.claude/launch.json`（端口）。
3. 写计划文件（plan 模式给的路径），结构固定：
   - **背景与结论**：三块变化（界面 / 内核 / 存档），以及"需不需要用户补信息"的明确结论。策划案把数值、进程参数、迁移规则、验收用例都给齐时，结论就是不需要。
   - **执行方式**：开发代理 + 试玩代理 + 本会话核对；提交约定。
   - **开发假设**：编号列表，只写"规则解释"（ID 写法、状态落在哪个类、Esc 顺序、迁移冲突时玩家看到什么、图片用占位等），不含任何数值。
   - **工程映射与里程碑**：编号接着上一轮（v0.4 用到 M25，下一轮从 M26 起），每个里程碑列文件、改法、测试；通常顺序是 配置与物品 → 模型 → 规则/tick → 拖拽与预览 → 存档迁移 → 界面 → 次级菜单 → 收尾（文档、README、SurvivalBot）。
   - **可直接复用**：函数与组件清单，让开发方别重写。
   - **验证**：`dotnet build web/Survival.sln`（`dotnet test` 只编译测试工程，网页壳的编译错误要靠它暴露）与 `dotnet test web/Survival.sln`、策划案里的验收编号（U/P 系列）、两档分辨率截图、旧档写入 `localStorage.survival.save.v1` 后点"继续"。新写的测试只要读了策划案数据文件（测试目录里的 `design.*.json`、`config.v0.2.json`）逐条对照，就在方法上加 `[Category("DesignSync")]`：CI 把这类单独一步跑、失败不拦发布（策划改数值先于实装时属预期差异），本地 `dotnet test` 照样全跑、要求全绿。
   - **试玩检查清单**：必走路线 + 报告格式。
4. 真正阻塞的空白（不问就只能补数值）用 `AskUserQuestion` 问；能用假设绕过的不问。然后 `ExitPlanMode`。

## 3 开发（开发代理）

用户批准计划后立刻开发。**注意**：批准计划之后的回合会被应用当作自动事件，`start_session` 会报"Start sessions only on the user's own words"，不要反复试；直接用 `Agent`：

- `subagent_type: "general-purpose"`，**不传 `model`**（继承本会话默认模型），在本工作区工作（不开 worktree）。
- prompt 必须自包含（代理看不到本会话）：项目背景与约定（第 0 节）、任务与提交规则（每里程碑一提交、不推送、Co-Authored-By 写代理自己实际的模型名）、先读哪些文件、**现有工程关键事实**（探索代理查到的路径与行号，直接贴）、**开发假设**全文、里程碑映射全文、可复用清单、完成标准（测试全绿、浏览器逐条走验收编号、两档分辨率截图、旧档验证、`preview_stop`）、最终汇报格式（提交号、测试数、手测逐条、偏差、待确认、资源缺失清单）。
- 告诉它遇到假设没覆盖的规则空白：选最保守做法继续并在汇报里列"待确认"，不要停下来等人。
- 手测用 `preview_start {name:"web"}`（5177，被占用 `web-alt` 5180），不要用 Bash 起服务器。
- **测试防假绿**（2026-11-16 用户定，取自参考方案的"假绿自查"和"改坏验证"）：把下面整段原样贴进 prompt。
  > 测试要验的是策划案，不是"现在代码跑出来是多少"。写完每条测试自查：
  > 1. 期望值来源：写字面量并在注释里注明出处（策划案 §条目 / Q 号 / 开发假设 A 号），或读测试目录里的策划案数据文件；不要从引擎自己用的配置或同一个函数里取出期望值再断引擎输出等于它（换成错的实现照样绿）。
  > 2. 断确切值：策划案给了确切值就断确切值，`Is.Not.Null`、`> 0`、`Is.Not.Empty` 只能当辅助断言。
  > 3. 不跳过因果：`Debug*` 只用来造起点，不要直接把结果态设上再断结果态。
  > 4. 断"不该发生"（拒绝、不触发、不显示）的，要另配一条"条件满足时确实发生"的测试，否则断言失灵或路径没走到也是绿的。
  > 5. 在集合 / 循环里断言的，先断数量符合预期（空集合时循环里的断言一条都没跑）。
  > 6. **改坏验证**：每条新规则挑它的关键测试，用 Edit 把实现的关键处改坏（判定条件取反、数值改掉、删掉那行调用），只跑这个测试类 `dotnet test web/Survival.sln --filter "FullyQualifiedName~<测试类名>"`，确认变红，再用 Edit 改回，`git diff` 确认实现已还原（不要用 `git checkout` 还原，会冲掉同文件里没提交的改动）。改坏了还绿，说明测试是假的，重写。
  > 7. **改已有测试的期望值**（数值、状态、文案、条数），或删测试、加 `[Ignore]`/`[Explicit]`：必须有出处（策划案条目 / Q 号 / 开发假设 A 号），写进测试注释和提交说明；"实际跑出来是这个"不算出处。确认是旧测试本身写错的，在汇报里单列说明。
  > 8. **网页壳的行为用 bUnit 测**（2026-11-19 用户定）：改到网页壳（`web/Survival.Web/Services/GameSession*.cs`、组件里的点击／输入／显示逻辑）的，在 `web/Survival.Web.Tests` 里写 bUnit 测试——继承 `WebTestBase`（已开新局、去开场剧情），用内核 `CreateItems`／`Debug*` 只造起点，再 `RenderComponent<组件>()`、`Find(...).Click()`／`.Change(...)`，断玩家看到的文字、属性和状态（样板 `B56WaterUiTests`）。选元素优先 `data-pt`／`data-*` 钩子，不按按钮文字找。CSS 布局、遮挡、滚动、拖拽 bUnit 看不到，仍靠试玩。改到某个组件时，`Survival.Core.Tests` 里读这个组件源码的旧断言顺手换成 bUnit（不专门大批迁移）。
  > 9. **源码字符串断言**（只留给没法渲染的接线，例如某组件是否挂在某处、样式表有没有某条规则）：用 `SourceText.Web("Components/X.razor")`／`SourceText.Code(路径)` 读（先去掉注释），不要拿注释当锚点；文案期望能从策划合同 JSON 取的用 `SourceText.Contract("<合同文件名>.json")` 取，不在测试里另抄一遍（样板 `B56UiWiringTests`）。能用内核常量或内核函数断言的（如 `FeedPanelCopy.HelpText`、`ConfigLoader.FromJson`）优先断内核，不读源码。
  >
  > 汇报加一张"改坏验证表"：测试名 → 改坏了哪（文件:行，怎么改）→ 是否变红；再加一张"改动的已有断言表"：测试名 → 原期望 → 新期望 → 出处。
- 要求它写 `doc/开发记录/<批次号或版本号> <主题>.md`（2026-11-11 起每个批次或每次接入各写一份，不再往 `doc/开发计划 v*.md` 里追加；格式照 `doc/开发计划 v0.3 卡片统一与设施烹饪.md`：映射、假设、实施记录与偏差、待确认、资源缺失）。下文说的"开发计划"都指这份文件。

代理结束后自己核对：`git log --oneline`、`git status`（应只剩别人的未入库文件）、`dotnet build web/Survival.sln` 0 错误与 `dotnet test web/Survival.sln` 全绿、看它的截图。

再核对测试有没有"改期望凑绿"（`<基线>` = 开发代理开工前的提交）：
- `git diff <基线>..HEAD -U0 -- web/Survival.Core.Tests` 里，以 `-` 开头、带 `Assert`/`Is.`/`Has.`/`Does.` 的行就是被改掉或删掉的已有断言；新增 `[Ignore]`、`[Explicit]` 和整条删掉的测试同样算。逐处对照代理汇报的"改动的已有断言表"：每处都要有策划案条目 / Q 号 / 开发假设出处，而且出处里确实是新期望。表里漏了或对不上出处的，`SendMessage` 退回开发代理：改回原期望并修实现，或补上真实出处。
- 汇报里没有"改坏验证表"，或有新规则没在表里出现，同样退回补做。

**变异测试**（2026-11-16 用户定；本批改了 `src/Core` 就做，只改界面、文案、样式的不做）：用 Stryker 把本批改动过的每一行引擎代码系统地改坏一遍（判定取反、比较符换向、数值和调用改掉……），看测试抓不抓得到。补的是第 6 条手工改坏验证的盲区：代理自己挑的改坏点往往是它知道会红的地方。B51b 试点：改动 273 行、180 个变异、28 个没被发现，其中约 19 个指向 5 处确实没测到的规则（Q703 提醒资格、可投批数、完工输入齐全、54→55 迁移暂停保质）。
1. 上面核对通过后，本会话后台跑 `python tools/stryker-batch.py <基线>`（Bash `run_in_background`，约 7 分钟；在系统临时目录的 worktree 里跑，不碰工作区 bin/obj，可以和第 4 步试玩同时进行）。没改 `src/Core` 它会直接说"不用跑"。
2. 跑完读它打印的 `survivors.md`：每条"存活"（改坏了测试仍全绿）或"无覆盖"（没有测试跑到）都要处理。整张表 `SendMessage` 给同一个开发代理：能对上规则的补测试（守上面"测试防假绿"9 条，期望值写出处）；不补的在开发记录"变异测试"一节逐条写理由，只认四种：等价改动（如分组非空时 `First`/`FirstOrDefault`）、纯日志分隔符、开发入口工具、观察不到的清理代码（2026-11-19 起 `GameEngine.Debug.cs` 与 `Debug` 开头的方法已不参与变异，一般不会再出现“开发入口工具”）。补测试只改测试；发现实现本身错了的按 bug 修。
3. 代理补完提交后再跑一次脚本（基线不变），确认补过的那些已被抓到。还剩的、理由不在四种里的再退一次；两轮后仍剩的写进开发记录遗留，不挡推送（这是测试缺口，不是游戏 bug）。
4. 开发记录"变异测试"一节写：两次的得分与存活数、处理表（位置 → 补了哪条测试 / 不补理由）。
- 跑了变异测试的批次，开发代理"测试防假绿"第 6 条手工改坏验证只做 `src/Core` 以外的（一般没有），给它的 prompt 里注明"src/Core 的改坏验证由变异测试代替"。
- Stryker 起不来（没装 `dotnet-stryker`、编译失败）→ 不挡流程，汇报里写明"变异测试没跑（原因）"，第 6 条照做。装法见脚本开头说明（本机 SDK 8.0 只能用 4.x）。

## 4 试玩（试玩代理）

**2026-11-24 起脚本为主**：先打本地 Release 包、本会话跑全量场景 `node tools/playtest/run.mjs`（约 2 分钟，回归交给它）；试玩代理的主要任务是把本次改动逐项写成场景 `tools/playtest/scenarios/<版本或批次>-<主题>.json` 并三档跑通，AI 只看改动画面的场景截图与截图差异，再对新功能做约 15 分钟的短时探索（体验、手感、文字、策划案意图）；复验 = 本会话重跑全量场景。具体照 `/git-watch` 第 4.1 节第 2—5 步（用户在场时探索部分可以用下面的内置浏览器看着做）。下面是探索部分与报告的要点。

`Agent`，`subagent_type: "general-purpose"`，`model: "opus"`、`effort: "high"`（本机钩子要求；本项目绝对不用 claude 命令行派活，见仓库 `CLAUDE.md`）。prompt 要点：

- 身份：真人玩家视角，**只玩和报告**，不改文件、不提交、不推送、不去线上地址。
- 背景：这次改了什么（按策划案要点写，让它知道预期），规则以哪份策划案为准，开发方解释在哪份开发计划；报告里要区分"与策划案不符"和"策划案如此但体验不好"。
- 怎么玩：`preview_start {name:"web-fb"}`（5190，专给试玩用），首次加载约 10MB 耐心等；`read_page`/`get_page_text`/`find` 读界面，`computer` 点击与 `left_click_drag` 拖拽，关键画面截图；视口 1280×720 为主、1600×900 复查；快捷键 M/C/R/L/Esc。
- 必走路线（写成场景；场景写不了的才手走）：从新游戏至少玩到本次改动涉及的目标完成（v0.4 是第 3 日目标），逐项列出要触发的交互（本次新增的每条路径、熄火复燃、超重拒绝、刷新读档、旧档迁移、Esc 逐级、拖拽中 Esc）。
- 全程留意：控制台报错、裁切重叠、热区过小、文案错误、图标缺失、数据不一致。
- 报告格式：试玩过程表（时刻、行动、六项状态，样式照 `doc/试玩评价与改进建议 v0.1.md`）、Bug 清单按严重度（复现、预期引用策划案条目、实际、截图文件名、报错原文）、验收对照（每条通过/未通过/未覆盖）、可以改进的地方、总体评价。结束 `preview_stop` 并 `resize_window {preset:"desktop"}`。

## 5 分类试玩结果

| 情况 | 处理 |
| --- | --- |
| 违反策划案条目、同一功能两条路径信息不一致、1280×720 裁切/热区 <40px、控制台报错、残留选中态 | **bug，交回开发代理修**：`SendMessage` 给同一个开发代理（它保留上下文），逐条写编号、复现、要求、截图文件名；要求一次提交（M 下一号，"试玩修复：…"）、测试全绿、两档分辨率亲自复验、在开发计划里加"试玩修复"一节 |
| 策划案没写但明显更好的小改（如可见的禁用原因） | 一并交给开发代理；要新写或改动玩家可见文字的不改，问文案策划 shioko0315（2026-11-16 起，`00 总则/05 文案设计归属与修改规则.md`） |
| 体验改进（提示时机、动画时长、数值手感）、策划案空白需要新规则 | **不做，列给用户拍板** |
| 开发代理汇报里的"待确认" | 原样转给用户 |

修完后**复验**：重新打包、本会话重跑全量场景（含本次新场景），全绿即通过；修的是显示、遮挡这类要看图的，才 `SendMessage` 给同一个试玩代理看那几张新截图（2026-11-24 起，不再让它逐条复走＋快速回归）。复验仍不过就再来一轮；两轮不过整理现象问用户。一两行能修的（比如一个 CSS 值）自己直接改并提交，不必再绕代理。

5. 单独一次提交 `文档：<版本> 策划案按实现补【实现同步】与修改记录`（只 add 改过的策划案与开发计划），并在开发计划文档里记一笔"已同步策划案：文件 + 条目"。
