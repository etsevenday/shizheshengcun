  `dependsOn` = 这一批开工前必须先做完的批次。**缺省（不写）= 依赖排在它前面的所有批次**，前面有挡队列的 `waiting` 批次它就不开；写了（可以是空数组 `[]`）就只看列出的批次，都做完就能开，不管别的批次在不在等。只有**确定**不和某一批改同一块代码、同一份存档结构、也不用它的产出时，才把那一批从依赖里去掉；拿不准就不写。拆分时定（第 2.3 节第 9 条），预检脚本照这个判断。
  `gapChecked` = 这一批已提前做过开工前核对、没有缺口（第 3.0 节第 5 条）。
  `held` = 用户挂起（2026-11-09 起；首例是 UI 重做 B31—B37，等用户评估策划补的效果图和图素）：不开工，也不挡别的批次，预检不算它待处理；`note` 写挂起原因和恢复条件。策划答复它的 Q 或推来它的素材都**不自动恢复**，只有用户在场明确说开工才改回 `pending`。
  `minor` = 次要问题攒批（2026-11-11 用户定，第 2.3 节第 8 条）：队列里最多一个，编号 `BM1`、`BM2`……；`questions` 是攒着的全部次要 Q（含未答的），`answered` 记已答的 Q 和策划答复提交的日期，`items` 是已答 Q 拆成的 R。不开工、不挡别的批次；满足开批条件时改成 `pending` 排最前，之后再出的次要 Q 进下一个 `BM`。
  `queue`、`pendingPlaytest` 可缺省。需求清单全文写在 `.git/claude-git-watch-queue.md`（第 2 节；每轮是新会话，scratchpad 不跨轮保留，所以放 .git 里）。
  **做完的批次不留在状态文件里**（2026-11-11 起；此前攒了 30 多个 done 批次，文件 35 KB，每次心跳都要整个读写一遍）：批次一 `done`，把它整条（含 `note`、`commits`、`questions`）追加进 `.git/claude-git-watch-done.json`（一个数组，没有就新建），再从 `queue.batches` 里删掉。每轮加锁后先看一眼，`queue.batches` 里还有 `done` 的就照此搬走。要查以前某批做了什么（接手中途死掉的一轮、核对某个 Q 是哪批提的）去 done 文件里用 Grep 找，不要整个读进来。预检脚本把不在 `queue.batches` 里的批次当作已完成。
  `queue.batches` 里没有批次了 → 把 `queue` 删掉、清单文件改名为 `.git/claude-git-watch-queue.<日期>.done.md` 留档；只剩还攒着 Q 的 `minor` 批次时保留 `queue`（`issue`、`source` 照留），清单文件照样改名留档。
- 凡是"通知用户、停下"的情况，同时把 `notifiedHead` 记为当前 origin/main；下一轮 origin/main 仍是这个提交就安静结束、不再重复通知，等用户处理或策划再推新提交。本轮成功推送后把 `notifiedHead` 清回 null。

## 1 加锁与检测（没事就安静退出）

0. **预检**（省 token）：定时任务提示词带 `[git-watch-scheduled]` 标记，本机 `.claude/settings.local.json` 的 UserPromptSubmit hook 会先跑 `python tools/git-watch-precheck.py --hook`：结论为 IDLE（锁未过期 / origin/main 已通知过 / 无新提交）时直接拦下提示词，模型不启动；WORK 或 ERROR 时把预检结论作为附加上下文放进来。上下文里已有 WORK 结论 → 下面第 2 步的 fetch 和列提交可以省掉，直接用它；没有（hook 没生效、手动触发）→ 先跑一次 `python tools/git-watch-precheck.py`，首行是 IDLE 就回一句结论结束，不用往下读。每次 hook 结论记在 `.git/claude-git-watch.log`。预检只读、不加锁，WORK 时仍从第 1 条开始加锁。
1. **加锁（心跳锁）**：读状态文件。`runningSince` 非空、且 `heartbeat`（缺省看 `runningSince`）距今不到 1.5 小时（2026-11-11 由 4 小时改：B40 那轮 11:55 卡住，白等到 15:11 才能接手） → 上一轮还在跑，直接结束，不通知、不动状态文件。预检判定上一轮已卡住的（会话记录 45 分钟没写入，见下）照常接手。否则生成本轮 `runId`（当前 ISO 时间 + 4 位随机），把 `runId`、`runningSince`、`heartbeat`、`sessionId` 写进去，记住自己的 `runId` 和 `sessionId`。`sessionId` 取本会话 scratchpad 路径里 `scratchpad` 上一级的目录名（形如 `f1b23ed9-c065-44c9-82e3-d2766b3f87bd`，对应 `~/.claude/projects/<项目>/<sessionId>.jsonl`）。
   - **会话卡住的判定**（2026-11-11 起）：后台心跳进程不随会话停下（B33 那轮 18:35 撞用量上限，心跳循环照样续锁到 20:33，后面每次预检都以为还在跑）。所以预检除了看心跳，还看 `sessionId` 对应的会话记录（主会话 jsonl 和 `<sessionId>/` 下子代理记录）最后写入时间：超过 45 分钟没动就当已卡住、交下一轮接手。正常干活时代理每条消息都会写记录，单条命令也别让它 45 分钟没输出。
   - **心跳**：每进入一个阶段都刷新 `heartbeat` = 当前时间：拆分完成、每起一个代理之前和它返回之后、每次提交前、推送前、等部署前、每轮试玩/修复前。刷新时先读出 `runId`：**不是自己的** → 说明锁已被别的轮次接手（本轮卡太久），立即停手：不提交、不推送、不改队列，`PushNotification`"git-watch 本轮 <runId> 锁被接手，已停下"，结束。
   - **清锁**：本轮无论怎么结束都要清锁，但**只清自己的**：读出状态文件，`runId` 等于自己的才把 `runId`/`runningSince`/`heartbeat` 置 null；不是自己的就不碰。
   - 单个代理别一口气塞太多活：一批的开发量控制在一个代理 1–2 小时内（第 2 节分批时就按这个量切）。**代理跑着的时候也要续心跳**：起代理（开发、试玩、分析）后，同时后台跑 `python tools/git-watch-heartbeat.py <runId> <sessionId>`（Bash `run_in_background`），它每 20 分钟刷新一次 `heartbeat`，`runId` 不是自己的或本会话记录 45 分钟没写入就自己退出；代理返回后用 TaskStop 停掉。不要再在 scratchpad 里临时写心跳循环。阶段间的单次刷新也可以用它加 `--once`。这样两次心跳之间不会超过 1.5 小时。
2. `git fetch origin`。看两样：
   - 新提交：`git log --format='%h %an %ad %s' <lastSeen>..origin/main`，只看作者不是 `etsevenday` 的。**不要用 `HEAD..origin/main`**：别的会话可能已把策划提交拉进本地 HEAD，那样会漏掉。
   - 队列：`queue.batches` 里有没有可开工的 `pending`（按第 0 节 `dependsOn` 判断，预检结论里已分好；上一轮留下的 `running` 说明那轮中途死了：看它的 `commits` 与 origin/main 判断做到哪，没推上去的改回 `pending` 重做，已推上去的按第 4.1 节从试玩接着做）。
   - 次要攒批：有 `minor` 批次、且满足第 2.3 节第 8 条的开批条件 → 改成 `pending` 排最前，当作有 pending 批次。
   两样都没有 → 清锁，结束，不通知、不汇报。没有策划新提交、`pending` 批次又都被 `waiting` 批次或没做完的依赖挡着 → 同样清锁结束。
3. 本地有正在进行的工作就不碰：`git log origin/main..HEAD` 有未推送提交，或 `git status --porcelain` 里有已跟踪文件被改（未跟踪文件如 `doc/策划案.7z` 不算）→ 说明别的会话正在干活。`PushNotification`："git 有策划新提交/待处理批次 <短号或批次号>，但本地有未推送/未提交的工作，没自动处理"，清锁，结束（`lastSeen`、队列都不更新；照第 0 节记 `notifiedHead`，别的会话推送后 origin/main 变了自然会接着做）。
4. 有新提交 → 第 2 节拆分（并入队列）；没有新提交、只有 pending 批次 → 跳过拆分，直接取队列里第一个可开工的 `pending` 批次进第 3 节。

## 2 拆需求清单、按主题分批（有新提交时做）

### 2.1 先看越界、再合入

先 `git show --stat <每个新提交>`。改到 `doc/策划案/` 以外的（下表 X）→ 不合入、不处理，`PushNotification` 告诉用户哪几个提交改了哪些文件，清锁结束，`lastSeen` 不更新。没有越界就合入：`git pull --rebase --autostash origin main`。冲突按 `/design-dev` 第 1 步第 2 条：策划原文以策划为准，本方【实现同步】与修改记录两边保留；两边改了同一句拿不准 → `git rebase --abort`，通知用户，清锁结束。

### 2.2 拆需求清单

改动很小（只答复几个 Q、或一两个文件的小修订）就不起代理，自己列清单、只分一批，照样写队列（2.4）。否则起一个**拆分代理**（`general-purpose`，不传 `model`，`effort: "high"`，brief 写明"只读，不改文件"），交给它：新提交的短号、提交说明全文（策划按 `AGENTS.md` 会按主题分组写，没分组就照逐文件变更与 CHANGELOG 最新一节自己归纳）、`git show <短号> -- doc/策划案` 的读法；队列里还没做的批次（有的话）也一并交给它重排。要它产出一份需求清单，每条一行，写清：

- 编号 R1、R2……（接着清单文件里已有的最大号）、一句话需求；
- 出处：文件 + §节 + 验收编号（如 `S06 §7 A09–A11`），同一需求散在几个文件就都列上；
- 类别：下表 A/B/C/D（一条只归一类）；
- 要动的代码区域（内核哪些类 / 网页壳哪些组件 / 存档迁移 / 只改文档）、依赖哪几条 R；
- 有没有数值空白、规则含糊（有就标"待确认"，这条不做，第 4 节写成问题）。策划按 `AGENTS.md` 上传前已自查：正文里标 `【交开发方定】` 的按其写的做法做、不再问（写进开发假设与【实现同步】）；标"待定"的跳过不做、也不再问；提交说明"上传前自查"里列过的点不重复问。只有自查漏掉的缺口才写成问题。

只是索引与汇总的改动（README、CHANGELOG、`00 总则/01 规则迁移与待定清单`、`04 附录/A04 验收索引`、`文档登记与来源快照.json`）不单列需求，挂在对应需求上。

### 2.3 分批

按下面的规则把需求清单分成批次（拆分代理给方案，本会话核对后定）：

1. **同一主题、互相依赖、改同一块代码的需求放同一批**（例：五卡上限 + 转移校验 + 锅算一张卡，即使分散在 S06/S07/S10）。**绝不按文件切**，一个文件里的不同需求可以分到不同批。
2. **每批的量**：一个开发代理 1–2 小时做得完，约等于以往 8–10 个里程碑以内；超了就按"内核规则 → 界面"或按子主题再切。
3. **顺序**：A 类答复里只改文档、或改一两处代码的放 B1；然后内核/存档相关；然后界面；被依赖的在前。D 类纯文档整理单独一批放最后（或挂进相关批）。
4. 整体量和以往一轮相当（一个主题、≤10 个里程碑）就只分一批，照旧一轮做完。
5. 新提交到来时队列里还有没做完的批次：已 `done` 的不动；新需求如果修订了某个未做批次的内容就并进那一批，否则按上面顺序插队或排在后面；策划答复（A）照样排最前。
6. **一组问题全答完才开工**（2026-11-10 用户定；此前策划把 Q246—Q251 拆两次推，B27 做完 Q251 才到，又多做一轮 R41）。"一组" = 待确认文档里同一节"## <日期> 来自 <提交> <批次号>"的全部 Q；`waiting` 批次的 `questions` 也算一组。"答完" = 这组每条的"策划答复"都不再是单纯的"待定"；`AGENTS.md` 约定策划确定不做的写成"待定（策划确认本次不做）：……"，这种算答完，对应部分跳过不做、写进 `note`。
   - **答的是 `waiting` 批次在等的 Q**：答复并进那一批（拆成 R 写进 `items`）。这组全答完 → 那批改回 `pending` 排最前，开发 brief 里写明每条结论；还有没答的 → 批次保持 `waiting`，`note` 写"已答 Qa、Qb，还差 Qc"，在 issue 下评论一句"已收到 Qa、Qb 的答复，还差 Qc，答完后开工"，本轮拆完就结束（`lastSeen` 照常前移，下次策划再推才会醒）。
   - **答的是不在 `waiting` 批次里的 Q**（试玩后、开发中提的问题）：同样按组看。全答完 → 照常开 A 批；还有没答的 → 已答的先并成一个 A 批，`status: "waiting"`、`blocksQueue: false`（不挡别的批次），`questions` 记整组 Q，`note` 与 issue 评论同上；等这组答完再改回 `pending`。
   - 策划的新提交一条都没答到 `waiting` 批次的 Q → 照常拆分入队；`blocksQueue` 不为 false 的 `waiting` 批次仍挡着排在它后面、没写 `dependsOn` 的批次，拆完后有可开工的批次就接着做，没有就结束。
   - 答的是次要 Q（在 `minor` 批次的 `questions` 里）→ 不按上面开 A 批，按第 8 条记进攒批。
8. **次要问题攒够再一起修**（2026-11-11 用户定；此前 B32b—B32g 每轮试玩冒出几条文案小问题，各开一批，连做了五个小批次）。
   - **算次要**：只涉及文案措辞、焦点、提示位置、显示细节，不改规则、数值、存档，不修玩家照常能玩。待确认文档里该 Q 标题末尾写"（次要）"，开发方提问时就按这个标准定。**不算次要、照旧处理**：线上 bug（照修，不问）；和已定规则冲突、不定就没法继续的（如 Q401 的 Q394 与 Q338 打架）；开工前核对出的规则、数值、存档缺口。
   - **平时**：次要 Q 照常写进待确认文档、随提交推给策划、issue 评论；同时记进 `minor` 批次的 `questions`（没有就新建，`status: "minor"`）。不为它开批次、不让任何批次 `waiting` 等它。策划答了 → 拆成 R 并进 `items`，`answered` 记 Q 与答复提交日期；同一节的其他 Q 还没答完的照第 6 条先不算已答。
   - **开批条件（任一满足）**：① `answered` 满 8 条；② 队列里没有别的 `pending`/`running` 批次，也没有挡队列的 `waiting` 批次（`held` 不算），且 `answered` 至少 1 条；③ `answered` 里最早的日期距今满 2 天。满足 → `minor` 改 `pending` 排最前，只做已答的 R，没答的次要 Q 移进新的 `minor` 批次接着攒。
   - **顺带修**：取一个主要批次开工时（第 3 节），看攒批里已答的 R 有没有和它改同一块界面或同一个文件的，有就挪进这一批一起做（从 `minor` 的 `items`、`answered` 删掉），不受上面条件限制。
   - 本条取代第 6 条里"答的是不在 `waiting` 批次里的 Q → 照常开 A 批"对次要 Q 的适用；主要 Q 照旧。
7. **属于 `held` 批次的新需求**（答复它的 Q、修订它的内容、补它要的素材）：并进那一批或新开一个 `held` 批次，状态保持 `held`，不开发；别的需求照常拆分入队。拆完 `PushNotification` 一行告诉用户"<批次> 的答复/素材已到，等你评估"（不记 `notifiedHead`，免得挡住别的批次；`lastSeen` 已前移，不会重复通知）；本轮有别的 `pending` 批次就照常接着做。
9. **写依赖**（2026-11-11 用户定，配合第 0 节 `dependsOn`）：拆分定批次时，逐批看它和排在前面的未完成批次有没有关系：改同一块代码或同一个界面、动同一份存档结构、要用前一批的产出（新字段、新面板、新配置），任何一条成立就是有依赖。**默认不写 `dependsOn`（= 依赖前面所有批次）**；只有逐条看过、确定都不成立时才写 `dependsOn: []`，只依赖其中几批的写那几批的编号。清单文件的批次说明里写一句理由（"B41 只动内核敌踪，与 B40 存档界面无交集"）。同一个策划包切出来的前后批次（如 UI 重做 B33—B37）一律不写。判断错了的代价是后一批建在缺东西的基础上返工，所以宁可多等。

### 2.4 写队列

- 清单写进 `.git/claude-git-watch-queue.md`：文首写来源提交与拆分时间；`## 需求清单`（每条一行，格式见 2.2）；`## 批次`（每批：编号、主题、包含的 R、类别、为什么这样分、状态）。已有文件就追加/重排，不删已 `done` 的记录。
- 状态文件写 `queue`（批次列表，`items` 填 R 编号，`status: "pending"`，按第 2.3 节第 9 条决定写不写 `dependsOn`），`lastSeen` = 拆分覆盖到的最后一个提交（第 1 节第 2 步 fetch 到的 origin/main；合入时又拉到更新的策划提交，没拆进来就别越过它），刷新心跳。**从这一步起 `lastSeen` 就前移**：后面的进度全靠队列记，某一批失败也不会把整个提交重来一遍。
- `PushNotification` 一行："策划 <短号> 拆成 N 批：B1 <主题>、B2 <主题>……，本轮先做 B1"。
- 然后取第一个可开工的 `pending` 批次进第 3 节。

### 2.5 类别

| 类别 | 判断 | 处理 |
| --- | --- | --- |
| X 越界 | 改到 `doc/策划案/` 以外（代码、`data/`、`web/`、`.github/`、`AGENTS.md` 等） | **不合入、不处理**。`PushNotification` 告诉用户哪几个提交改了哪些文件，清锁结束，`lastSeen` 不更新 |
| A 答复 | 改了待确认问题文档里的"策划答复"栏（从"待定"变成结论） | 第 3.1 节 |
| B 修订 | 改了已有策划案的规则或数值（S/R 系统案、旧版本文件） | 第 3.2 节 |
| C 新策划包 | 新增版本目录（`doc/策划案/<名称> v<号>/`）或大面积新增玩法 | 第 3.3 节 |
| D 整理 | 只是重排、改措辞、补说明，没有规则/数值变化（如 v1.0 重编） | 第 3.4 节 |

拿不准 B 还是 D：逐条比对改动句与当前实现（`data/config.v0.6.json`、`src/`），有任何一条要改代码就是 B。

## 3 做一批（一轮只做一批）

取队列里第一个可开工的 `pending` 批次（`held`、`minor` 批次跳过；被 `waiting` 批次或没做完的依赖挡着的也跳过，第 0 节 `dependsOn`），状态改成 `running`、刷新心跳；按第 2.3 节第 8 条看攒批里有没有可顺带修的 R。只做这一批包含的 R：读 `.git/claude-git-watch-queue.md` 里这些 R 的出处，按它们的类别走下面 3.1–3.4（一批里有几类就几种都走）。给开发/试玩/文档代理的 brief 里写清"本批只做 R…；同一提交里的其他需求属于后续批次，不要顺手做"。

- 开发前先走 3.0 开工前核对（顺带提前核对下一批，3.0 第 5 条）；本批有缺口就整批挂起，不往下走。
- 文档同步（`/design-dev` 第 6 步）只给本批做过的需求补【实现同步】与修改记录；后续批次的条目还没实现，不写【实现同步】、不当作偏差。
- 本批做完（推送、线上试玩复验都结束）→ 批次 `status: "done"`，`commits` 记本批提交短号，`questions` 记本批新增的 Q；试玩两轮仍有没修好的，照样 `done`，遗留写进 `note`。然后按第 0 节把这条搬进 done 文件。
- 本批受阻（测试不绿修不好、推送前拉到冲突的策划提交等第 5 节要停下的情况）→ `status: "blocked"`，`note` 写原因，记 `notifiedHead`，通知用户，清锁结束；后面的批次等用户处理后再继续（不跳过去做，免得在不稳的基础上叠改动）。
- 一轮只做一批：做完就走第 6 节收尾结束，下一批留给下次定时触发（10 分钟后）。

各类的做法：

### 3.0 开工前先把问题问完（2026-11-03 起，每批都做）

1. 起开发代理之前，逐条核对本批的 R 能不能不问就开工：先 Read `AGENTS.md`（2026-11-11 起它不再自动加载进上下文），按其"上传前自查"第 2 步那张表（数值、名词、作用范围、时机与持续、边界、敌人与自动行为、入口、来源、冲突、依赖未完成系统、旧存档）。C 类在 `/design-dev` 第 2 步的分析代理里一并做（brief 里写明要它列缺口）；A/B/D 小批次自己读出处做，不另起代理。答复批次（A）只看结论有没有含义不清或引出新空白（第 3.1 节第 3 条）。
   - **判断标准（2026-11-04 收紧）：凡是要开发方自己定规则、口径或玩家可见文字的，都算缺口，要问策划。** 不看"能不能先开工"，开发方能想出一个合理做法也算缺口。B23、B24 就是把这类地方算成"无阻塞缺口"写进开发假设，先上线后才问，Q215、Q217、Q223 都返工了。包括：
     - 策划案没写的规则、判定口径、取值、默认行为（什么算"可交"、原料从哪拿、中途失败怎么办）；
     - 玩家能看到的文字，策划案和数据里没有原句的（提示句、按钮名、原因句、任务台词）。只把策划给的字段填进句子不算；
     - 现有内容拿来顶替策划没给的内容（借用通用台词、沿用别处写法）；
     - 与策划案写法不同的做法，哪怕策划案写法实际不好用。
   - 只有这些不算缺口，开发方自己定、写进开发假设：代码结构、内部命名、像素与排版、动画快慢。开发假设里不许出现规则、口径和玩家可见文字。
   - 正文标 `【交开发方定】` 的照它写的做、标"待定"的跳过不做，都不问；已答复的 Q 或策划案其他处**写明了**结论的不问（要靠推测才得出的算缺口）。
   - 队列清单里拆分时写的"开发假设"不算数，开工前按这个标准重审一遍。
   - 分析代理的 brief 里把上面的标准原样写进去，要它列出"不问就得开发方自己定"的全部地方；不要写"不问就没法开发""阻塞缺口""别硬凑问题"这类说法。
   - 次要缺口（第 2.3 节第 8 条的标准）不挡本批：那部分不做，写成问题标"（次要）"、进攒批；只有次要缺口时本批照常开工。
2. **有缺口（不含次要的） → 整批不开发**：
   - 按第 4 节格式把缺口写进待确认文档（"游戏现状"写现在游戏里实际怎样，还没有的写"未实现，等策划答复"；仍写 A/B 选项和开发方建议，但**不实现**）。一轮最多约 8 条，按影响开发的程度排。
   - 只提交这份文档：说明 `M<n> 文档：<批次> 开工前待确认 Qx–Qy`，末尾照第 5 节写"待策划确认"段和"批次"行；按第 5 节推送（只改文档，跳过 build/test，不试玩）。
   - 第 6 节开 issue 或在已有 issue 下评论，正文注明"本批开发已暂停，等答复后继续"。
   - 批次 `status: "waiting"`，`questions` 记这些 Q，`note` 写"开工前等策划答复 Qx–Qy"；`PushNotification` 一行："<批次> 开工前有 N 个问题已发给策划（issue #n），开发暂停等答复"；清锁结束。
3. 没有缺口 → 往下按类别开发。开发代理 brief 里加一句："遇到策划案没写清、只能由开发方自己补规则/数值/玩家可见文字的地方，不要按推荐做法实现：那部分先不做，在汇报里列出（在哪、缺什么、可选做法）。" 这句不留例外，不写"计划已覆盖的除外"。它汇报的缺口按第 4 节写成问题，随本批推送；答复后作为 A 批补做。
4. 试玩修复同样守这条：违反策划案的 bug 照修；修法要开发方自己定规则、口径或玩家可见文字，或者觉得策划案写法本身不好用（如 Q225 确认窗挡路线），不改，写成问题等答复。
5. **顺带提前核对下一批**（2026-11-11 用户定：问题早一批发出去，策划可以在本批开发的一两个小时里先答，不用等本批上线后才发现下一批的缺口）。
   - 对象：只看**紧接着的下一批**——队列里排在本批后面的第一个 `pending` 批次，且没有 `gapChecked`、类别不是纯答复（A）。只前置这一批，不再往后看；它后面的批次等它开工时再前置。
   - 时机：和本批的核对同时做，在起本批开发代理之前（这时工作区还是干净的，问题可以单独推）。本批是 C 类、起了分析代理的，下一批另起一个只读分析代理并行跑；小批次自己读出处做。
   - 下一批没有缺口（或只有次要缺口，照第 1 条进攒批）→ 给它记 `gapChecked: "<日期> <origin/main 短号>"`，状态不变。
   - 下一批有缺口 → 照第 2 条写进待确认文档，**单独开一节**（节标题写下一批的批次号，末尾注明"提前核对"），不和本批的问题混成一组：策划可以分开答，"一组全答完才开工"（第 2.3 节第 6 条）也各算各的。下一批改 `waiting`、`questions` 记这些 Q、`note` 写"提前核对，等 Qx–Qy"。和本批的问题（有的话）同一次提交、同一次推送、同一条 issue 评论里分两段写。
   - 本批没有缺口、只有下一批有 → 推完下一批的问题后，本批照常往下开发，不停。
   - 提前问的问题可能因本批的实现而过时：本批做完后，开发记录里有涉及下一批那些 Q 的改动，就在对应 Q 下追加一行 `开发方补充：<本批已怎样做，这个问题现在变成什么>`，随本批文档提交推上去。
   - 下一批轮到开工时：有 `gapChecked` 的不重做整套核对，只看两样——`gapChecked` 之后策划有没有改过它的出处文件（`git log <短号>..HEAD -- <文件>`）、前一批的实现有没有让它的出处多出新缺口；都没有就直接开发。

### 3.1 A 策划答复了待确认问题

对每条有结论的 Q：
- 结论与现状一致（"保持现状""采纳现行口径"）→ 只改文档：把相关【实现同步】处按结论整理（原文就地改成与实现一致的说法或保留注释并注明"已经策划确认"），在待确认文档该 Q 下加一行 `处理结果：已处理（日期，提交 <短号>）：……`。
- 结论要求改行为 → 按 `/design-dev` 第 8 节第 2 条走小流程：开发代理改代码（一次提交，测试全绿）→ 有界面或玩法变化就起试玩代理复验 → 第 5 节推送。然后同上更新文档与"处理结果"。
- 策划写了结论但含义不清、或引出新数值空白 → 不猜，在该 Q 下追加 `开发方追问：……`，算作本轮的新待确认项。

### 3.2 B 修订已有策划案

按 `/design-dev` 全流程，但规模按改动大小裁剪：小改（几条规则/数值）不用两个 Explore 代理，自己读代码定改法，直接交一个开发代理；试玩代理只走改动涉及的路线并做一轮快速回归。新规则推翻了旧【实现同步】时按新规则做，修改记录里写明。

### 3.3 C 新策划包

完整走 `/design-dev` 第 1–6 步，按第 4 节的无人值守改法。计划写在 scratchpad 的 `plan.md`（不进 plan mode），里程碑编号接着 git 里最新的 M 号往下排（`git log --grep='^M[0-9]' -1 --format=%s`）。

**每个批次一份开发记录**（2026-11-11 起，A/B/C/D 各类批次都一样；此前同一队列共用一份开发计划、每批加一节，`doc/开发计划 v0.9 全系统扩展.md` 涨到 1.1 MB，谁读谁慢）：开发代理把本批的内容写进新文件 `doc/开发记录/<批次号> <主题>.md`，结构照旧（来源与范围、工程映射与里程碑、开发假设、实施记录与偏差、试玩修复、线上复验结论、遗留），写法照 `doc/开发计划 v1.0 重墨V2 UI重做.md` 里任意一个批次节。本技能和 `/design-dev` 里说"写进开发计划""开发计划加一节"的地方，都指这份文件。`doc/开发计划 v*.md` 旧文件留作历史，**不再往里追加**，也不拆；要查旧批次做法用 Grep 按批次号或 M 号找，不要整份读。

### 3.4 D 纯文档整理

不改代码。对照当前实现给新文本补【实现同步】与文末修改记录（做法照本仓库提交 49603af：只追加、不删改策划原句，每条写当前实际做法与出处，数值先核对 config/代码）。推翻现状、或含义不清的地方写成待确认问题。

### 4.1 无人值守试玩

内置浏览器的 `preview_start` 在定时回合里会被应用拦下要人点确认（2026-10-27、10-28 实测，settings 放行无效），所以无人值守**不用内置浏览器**。用户 2026-10-28 定：**先推送上线，再对线上网站自动试玩并修改**，期间线上有 bug 可以接受。

流程（改了玩法或界面时）：
1. 开发代理完成、测试全绿、文档同步 → 按第 5 节推送，等 GitHub Pages 构建成功（线上页脚"构建 <日期> · <短号>"显示本次推送的最后一个提交号才算部署到位；之后再推纯文档提交不会重新构建，页脚停在这个号上是正常的）。
2. 起**试玩代理**（Agent，general-purpose，不传 model，effort high），只用 Bash 跑 `node tools/playtest/cdp.mjs`（零依赖无头 Chrome，不需要任何人点确认；用法见文件头注释：`start / open / find / clicktext / click / drag / wheel / key / eval / text / shot / errs / size / stop`），对 `https://etsevenday.github.io/shizheshengcun/?dev=1` 试玩。brief 照 `/design-dev` 第 4 步写（改了什么、规则在哪、必走路线、三档分辨率 `size 1280 720` / `1600 900` / `1920 1080`、报告格式），截图存 scratchpad 后用 Read 看。告诉它：每条 Bash 只写一条 `node tools/playtest/cdp.mjs <命令> …`（在仓库根目录、相对路径、不用变量、不和别的命令用 `;`/`&&` 串起来），这样才匹配本机 settings.local.json 的放行规则、定时回合里不弹确认；每步操作后用 `text`/`find`/`eval` 读界面确认结果；`clicktext` 报"被遮挡/禁用"要记下；结束 `stop`。这个无头浏览器有独立的配置目录，不会碰用户自己浏览器里的存档。
3. 分类试玩结果（`/design-dev` 第 5 步）：bug 交同一个开发代理修（一次提交 `M<n> 试玩修复：…`、测试全绿、开发计划加"试玩修复"一节），推送，等部署，再 `SendMessage` 给同一个试玩代理在线上复验 + 快速回归。最多两轮；两轮仍不过 → 把剩余问题写进开发计划与提交说明，`PushNotification` 告诉用户哪些还没修好（线上已是最新提交，不回滚）。体验问题写成待确认问题；属于次要的标"（次要）"进攒批（第 2.3 节第 8 条），不为它另开批次。
4. 待确认文档里相关 Q 的"处理结果"写"已上线，线上无头浏览器试玩复验通过"（或列出仍未修好的）。
5. 万一 `cdp.mjs` 也跑不起来（找不到 Chrome、网络不通）→ 状态文件记 `"pendingPlaytest": ["<提交短号>", …]`（追加），`PushNotification` 写明"已上线、未试玩"；下次用户在场的会话（手动 `/git-watch` 或用户说"试玩一下"）开头先看它，非空就补试玩、修、推，然后清空。

- 用户在场、想看着试玩时也可以用内置浏览器：本会话 `preview_start {name:"web-fb"}`（5190），让试玩代理复用这台、别自己 preview_start；开发代理自测用 `web`（5177）/`web-alt`（5180）。本地 dev 服务器的 js/css 带固定 `?v=dev`，可能拿到缓存旧文件，试玩前强制刷新（线上 pages.yml 换成提交号，不受影响）；服务器要 stop 再 start 才加载新版本。
- 试玩手法：`?dev=1` 后菜单里有开发入口（测试箱含烤肉/水煮肉、放各种敌人、普通活性物质、跳日期等）；要触发暂停层，可在 `localStorage['survival.save.v1']` 里把 `Stats.Energy` 改到略高于低体力线再开行动；动存档前先另存一份到 `qa.backup.*`。批量连点时注意战斗结束后界面切回地块，同一坐标可能点到敌踪卡误接敌。
- 试玩只记录现象：违反策划案的交开发代理修（第 5 步规则），体验问题写成待确认问题。

写待确认问题的格式：在待确认文档"## 修改记录"之前新增一节 `## <日期> 来自 <策划提交短号> <批次号>（<一句话主题>）`（只有一批就不写批次号；每批各开一节），编号接着文档里最大的 Q 往下（Q6、Q7……）。拆分时就标了"待确认"、整批没法做的需求，在它所属批次那轮写成问题。每条照 Q2 的样子写：总册写法 / 游戏现状 / 请确认（A、B 选项，A 为开发方建议）/ `策划答复：待定`。2026-11-03 起不再写"已先按 A 实现"：缺口所在的部分等答复再做，"游戏现状"如实写"未实现，等策划答复"（问的本来就是已上线行为的除外）。文末修改记录加一行。

## 5 推送条件与提交说明

**推送条件（全部满足）**：`dotnet build web/Survival.sln` 0 错误；`dotnet test web/Survival.sln` 全绿；改了玩法或界面时的试玩放在推送之后做（第 4.1 节：推送 → 线上无头试玩 → 修 → 再推）；文档已按 `/design-dev` 第 6 步同步。只改文档的跳过前三条。（2026-11-02 起 CI 不再因策划案先于实装而失败：只改 `doc/策划案/` 的推送不触发构建；`[Category("DesignSync")]` 对照测试在 CI 单独一步、失败不拦发布。本地推送前仍要 `dotnet test` 全绿；推送后 `gh run view` 里"策划案对照测试"一步若标黄，说明还有策划改了的数值没实装，要排进队列。）

**提交说明**：本轮最后一个提交（通常是文档同步那次）的说明末尾、`Co-Authored-By` 之前必须有这一段：

```
待策划确认（N 项）：doc/策划案/系统策划总册 v1.0/00 总则/02 开发方待确认问题.md Q6–Q8
- Q6 <一句话>
- Q7 <一句话>
```

没有新问题就写 `待策划确认：无`。另起一行写 `来源：策划提交 <短号>…`。分了批的再加一行 `批次：B2/4 <主题>（R5–R9）；剩余 B3 <主题>、B4 <主题>`（最后一批写"剩余：无，本次策划提交已全部处理"）。

**推送**：推送前刷新心跳（第 1 节，`runId` 不是自己的就不推）。先 `git fetch origin`，看 `git log HEAD..origin/main` 有没有策划新提交，再 `git pull --rebase --autostash origin main`（拉取和推送不串在一条命令里）。拉到策划新提交时按下面分情况：
- **答复的只是本批的问题、且那一组已全答完（第 2.3 节第 6 条），`git merge-tree` 预演无冲突**（2026-11-04 用户定，11-10 加"全答完"）→ **自动并入本批继续，不停下、不通知用户**：拆成新的 R 并进本批（写进清单和 `items`），`lastSeen` 前移；按第 3.0 节核对答复，再按答复改代码和文档，测试全绿后回到这里推送。"本批的问题"= 本批 `questions` 里的 Q，或本批开工前、开发中提的 Q；策划为这些 Q 同步改到的其他策划案和合同也算。答复含义不清或引出新缺口 → 按第 3.0 节写成问题、批次 `waiting`，不算受阻。
- 答复的是本批的问题、但那一组还有没答的，预演无冲突 → 不并入、不按它改，照常推本批已做的；`lastSeen` 不越过这个提交，下一轮按第 2.3 节第 6 条处理（等这组答完再开工）。预演有冲突同下条。
- 改到本批涉及的策划案文件，但不是答复本批问题（别的修订、别批的 Q），或预演有冲突 → 不推，批次记 `blocked`，通知用户，清锁结束。
- 只改了别的文件 → 照常推，下一轮会把它拆进队列。

没有上面要停的情况就 `git push origin main`。**这次推送只改了 `doc/`、`AGENTS.md`、`README.md`、`.claude/`、`tools/` 的不触发构建**（2026-11-11 起，`pages.yml` 的 `paths-ignore`）：推完就算完，不用等构建、不用看线上页脚；这时 `gh run list --limit 1` 拿到的是上一次推送的构建，别拿它当本次的。推送里有别的文件（代码、`data/`、`.github/`）才往下：`gh run list --limit 1 --json databaseId,status,conclusion,headSha` 拿 run id（`headSha` 应是刚推的提交），`gh run watch <id> --exit-status --compact`；失败读日志修，修不了通知用户。成功后 `curl -s -o /dev/null -w "%{http_code}" https://etsevenday.github.io/shizheshengcun/` 应为 200。

## 6 通知与收尾

1. **提醒策划**（本轮有新待确认问题，或处理完了策划的答复时）。一个队列只开一个 issue：`queue.issue` 为空 → 按下面开新 issue 并把号记进 `queue.issue`；已有 → 在那个 issue 下 `gh issue comment` 追加本批的新 Q（同样的正文格式，标明批次）。用 `gh` 在仓库开 issue，指派并 @ 策划，GitHub 会给他发邮件和站内通知：

   ```bash
   gh issue create --repo etsevenday/shizheshengcun --assignee dotpad1994 --label 待策划确认 --title "待策划确认：<主题>（Q6–Q8）" --body-file <scratchpad 里写好的正文>
   ```

   正文：`@dotpad1994` 开头；一句话说明开发方已按哪次策划提交处理完并上线；列出每个 Q 的一句话与文档链接（`https://github.com/etsevenday/shizheshengcun/blob/main/<URL 编码后的待确认文档路径>`）；提交链接；最后写"请在文档里每条的'策划答复'一栏填结论后推送，开发方会自动处理"。标签 `待策划确认` 不存在时先 `gh label create 待策划确认 --repo etsevenday/shizheshengcun --color D93F0B`。
   处理完策划的答复后：在对应 open issue 下 `gh issue comment` 写明每个 Q 的处理结果；全部 Q 都已处理就 `gh issue close`。用 `gh issue list --repo etsevenday/shizheshengcun --label 待策划确认 --state open` 找 issue。
   本批是开工前挂起（第 3.0 节）的，issue 正文/评论里写明"本批开发已暂停，等答复后继续"，让策划知道答得越快开发越快。
2. **告诉用户**：`PushNotification` 一行：处理了哪个策划提交的哪一批、是否已上线、几项待策划确认、还剩几批（例："策划 82151fb B2/4 地图箭头已上线，1 项待策划确认（issue #5），剩 B3、B4"）。最终消息按 `/design-dev` 第 7 步的四段写，并附队列现状（每批一行：编号、主题、状态、提交）。
3. 更新状态文件：本批状态与 `commits`/`questions`/`note`（第 3 节）；`notifiedHead` 成功推送后清 null；队列全部 `done` → 删 `queue`、清单文件改名留档（第 0 节）；最后按第 1 节**只清自己的锁**。`lastSeen` 在拆分时已前移（第 2.4 节），这里不再改。
4. 流程有新经验写进记忆 `git-watch-automation.md`。
