## 职责边界

| 负责人 | 决策内容 | 不得越界 |
| --- | --- | --- |
| 文案策划 shioko0315 | 已定含义下的名称、标题、描述、帮助、提示、日志、对白表达、角色口吻、标点、术语统一、冗余压缩及具体逐字定稿。 | 不自行改变机制、数值、时长、概率、对象、条件、后果、可操作权限；不以精简删掉唯一必要事实。 |
| 用户 | 玩法机制、UI布局与流程、信息架构和显示字段／位置／时机、数值及其计算、开放条件与权限、表现规则，以及其他非文案设计。 | 不再把纯措辞题送用户逐句决策；文案不得反向替用户决定UI或玩法。 |
| 开发方 | 重新审查原Q、提供真实现状与复现、识别技术笔误／异常护栏、落实GitHub指派和原批追踪、按已定规则实现验证。 | 不能把纯实现细节或测试造损包装成待策划玩法；不因转交文案擅自选择设计选项。 |
| 总控 | 保留原批边界、协调双方答复、核对语义与跨案一致性、同步正文和逐字稿、完整原批检查后交付。 | 不把推荐当任何一方已答，不再以“总控补齐文案”代替新文案负责人的实际答复；不要求用户再次批准已定范围内的纯文字。 |

“写在哪里／何时显示／显示哪些事实或控件”属于UI设计；“同一已定槽位里的句子怎么说、术语怎么统一”属于文案。一个Q同时包含两者时保留同一Q号，分别标“Q号-设计”“Q号-文案”作为责任子项，不另编开发Q，也不把整题扔给一方。文案发现缺少真实规则时，只把具体缺口交回用户，不自行补数值或虚构玩法。

过去“纯文案由总控／开发补齐”的宽泛执行分工从本次起改为由文案策划负责，既有已经定稿文字和用户已定规则不自动推翻。用户此前要求精简、少量空格提示及游玩不反复提示Enter等规则继续生效；UI位置已有明确授权者沿原授权执行，不因岗位加入重新问一遍。新剧情分支、任务条件等实质设计不因含对白就全部转给文案。
